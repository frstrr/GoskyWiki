# Claude API Prompt Caching 失效根因与优化策略

## 背景

在一次长会话中（50+ 轮、200k+ token），使用 AI 编码助手完成属性系统分析、方案设计、代码实现、测试、code review 修复等全流程，发现 API 后台缓存命中率接近 0，导致高额费用。

## 核心机制

Claude API 的 prompt caching 基于 **前缀匹配**：只有对话历史的前缀部分完全一致时才能命中缓存。一旦中间某个位置的内容变了，从该位置开始后面的所有 token 都不会命中。

## 为什么长会话几乎不可能命中缓存

### 1. 对话上下文极长

每次请求都要把完整对话历史发给 API，几十轮对话累积的 token 数量巨大。

### 2. 工具调用结果是动态的

每一轮穿插的工具调用结果都不同：

- `git status` / `git diff`：每次输出不同。
- 编译检查：时间戳和错误列表每次不同。
- 文件读取：文件内容随修改持续变化。
- 测试结果：每次运行都是新数据。

这些动态内容插在对话中间，从第一个变化点开始，后面所有内容都无法前缀匹配。

### 3. 高频循环模式

“改代码 → 编译 → 跑测试 → 读日志 → 再改”这种循环，每一轮都会在对话中间插入大量不可能和上一轮一样的内容。

### 4. 单会话持续时间太长

如果拆成多个独立会话，每个新会话的 system prompt 和 AGENTS.md 部分可以命中缓存；但把所有工作塞在一个超长会话里，每次请求的 input token 都很大且几乎没有前缀可以复用。

## 优化策略

### 短期：拆分会话

- 每完成一个阶段性提交后，开新会话。
- 新会话里简要描述当前状态和下一步目标。
- 让 system prompt / AGENTS.md 这些固定前缀能命中缓存。

### 中期：减少单轮动态内容

- 把“编译 + 跑测试 + 读结果”合并成一个脚本一次性执行。
- 减少中间插入的动态 tool result 数量。
- 每轮工具调用结果越少，下一轮前缀匹配概率越高。

### 长期：本地中间层

- 把编译验证、测试运行、日志对比封装成本地命令。
- 只把最终结论（通过/失败/差异项）作为简短文本传给 AI。
- 大幅减少每轮对话插入的动态内容体积。

## 关键数据

| 指标 | 估算值 |
| --- | --- |
| 总轮次 | 50+ |
| 每轮平均工具调用 | 3~6 次 |
| 每次工具结果平均 token | 500~2000 |
| 累计上下文 | 200k+ token |
| 缓存命中率 | 接近 0% |
